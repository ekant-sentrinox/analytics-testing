# Configuration

Two layers, kept apart on purpose:

| | | used by |
|---|---|---|
| `.env` | **wiring and secrets locations** — hosts, ports, credentials paths | shell scripts |
| `config/*.yaml` | **tunables** — rates, thresholds, JVM and DuckDB settings | deploy scripts and the generator |

Nothing important lives in source. The rendered service configs on the servers
are generated from templates and are gitignored, because they are outputs.

### Auth

| Variable | Notes |
|---|---|
| `OTEL_JWT_SECRET_B64` | 64 random bytes, base64. Generated by `scripts/gen-secret.sh`. Shared by the generator and the collector — **rotating it requires redeploying the collector**, or every export returns `UNAUTHENTICATED`. |
| `OTEL_INGESTION_QUEUE` | `logs`. Becomes the `x-dd-ingestion-queue` JWT claim, and must match an `ingestion_queue` in the collector mapping. There is no default queue: a mismatch is `INVALID_ARGUMENT` on every request. |

64 bytes matters: at ≥64 the generator signs HS512, below that HS256. `jjwt`
sizes the algorithm to the key, so a short key produces tokens the collector
rejects.

## `config/generator.yaml`

### `generator.target`

| Key | Default | Notes |
|---|---|---|
| `host`, `port` | from `.env` | |
| `tls` | `false` | the collector serves plaintext here |
| `rpc_timeout_seconds` | `60` | **Do not set this low.** The RPC does not ack until the batch is durable, so a slow flush is latency, not failure. A short deadline turns a working pipeline into `DEADLINE_EXCEEDED` and undercounts accepted records. |

### `generator.workload`

| Key | Default | Notes |
|---|---|---|
| `target_rps` | `1000` | offered records/s. **Not throughput.** |
| `duration_seconds` | `60` | |
| `workers` | `8` | threads sending RPCs |
| `channels` | `4` | gRPC channels, shared round-robin |
| `batch_size` | `500` | records per export RPC. Raising it lowers RPC overhead and lets a 2-vCPU generator reach a higher record rate. |
| `max_inflight` | `64` | hard cap on outstanding RPCs. When hit, the pacer records `stalled_ms` instead of slowing down. Must be ≥ `workers`; the config rejects otherwise, because a bound below the worker count is never observable. |
| `retry_mode` | `none` | `none` \| `polite`. `polite` honours the server's `RetryInfo`. Recorded in every manifest either way. |
| `abort_on_consecutive_failures` | `0` | 0 disables |

### `generator.data`

Shapes the payload. `seed` makes it deterministic: same seed, byte-identical
record stream, which is what makes compression and file-size comparisons valid
across runs.

`body_bytes` (default 256) pads with random hex rather than a repeated
character — a run of `x` would compress to nothing and flatter every ZSTD ratio.

`model_traffic` adds `gen_ai.*` attributes: model name, input/output/total
tokens, and per-request cost derived from the `pricing` table (USD per 1M
tokens). Set `enabled: false` for plain log traffic.

`severity_mix`, `http_status_mix` and `latency_ms` are weights and percentile
anchors for the synthetic values.

### `profiles`

Each profile overlays `generator.workload`. Precedence:

```
CLI flags  >  profile  >  generator.workload
```

`steps:` turns a profile into a staircase — a list of `{rps, duration_seconds}`
run back to back, each sample tagged with its step index.

`stop_when:` (stress) ends the ladder on `accepted_ratio_below`,
`error_rate_above` or `latency_p99_ms_above`.

`fault:` (recovery) declares which component to disturb, how, and when.

## `config/collector.yaml` → SERVER 2

Read by `deploy-collector.sh`, which renders
`collector/config/application.conf.tmpl`.

| Key | Default | Notes |
|---|---|---|
| `jvm.max_heap` | `2g` | of 7.6 GiB. Arrow buffers and DuckDB are **off-heap**, and there is no swap — a large heap starves them. |
| `jvm.opts` | G1, `ExitOnOutOfMemoryError`, GC log | exiting on OOM is deliberate: a restart is visible in the metrics, a wounded JVM is not |
| `ingestion.min_bucket_size` | `16777216` (16 MiB) | **the most consequential knob.** Sets Parquet file size, which sets compaction load. |
| `ingestion.max_delay_ms` | `5000` | flush even when under `min_bucket_size`; the floor on visibility lag at low rates |
| `ingestion.max_pending_write` | `524288000` (500 MiB) | above this the queue raises `PendingWriteExceededException` → gRPC `RESOURCE_EXHAUSTED` |
| `duckdb.threads` | `2` | = vCPUs |
| `duckdb.memory_limit` | `2GB` | |
| `duckdb.temp_directory` | `/var/tmp/duckdb-collector` | **not `/tmp`** — `/tmp` is tmpfs on Amazon Linux 2023, so spilling there consumes RAM on a swapless box and converts a disk spill into an OOM kill |

Trade-off worth stating: raising `min_bucket_size` produces fewer, larger files
(less compaction work) but raises visibility lag and the memory held per queue.
Lowering it does the opposite. This is the first pair to move when the backlog
trends up.

## `config/compactor.yaml` → SERVER 3

| Key | Default | Notes |
|---|---|---|
| `schedule.minor_compaction_frequency` | `1 minute` | |
| `schedule.major_compaction_frequency` | `10 minutes` | shortened from the module default of 1 hour so a 10-minute staircase step contains several cycles |
| `schedule.housekeeping_frequency` | `5 minutes` | `expire_snapshots` + `cleanup_old_files` |
| `schedule.snapshot_retention` | `15 minutes` | |
| `sizes.minor_compaction_max_size` | `8MB` | files below this are merge candidates; also the small-file threshold the exporter reports |
| `sizes.major_compaction_max_size` | `64MB` | |
| `duckdb.*` | as collector | `temp_directory` = `/var/tmp/duckdb-compactor` |

**A major run replaces that tick's minor run**, it does not run alongside it.
See [ARCHITECTURE.md](ARCHITECTURE.md#compaction).

If you lengthen staircase steps, lengthen these in proportion. Changing the step
duration alone changes what "backlog slope" means and invalidates comparison
with earlier runs.

## `config/duckdb.yaml`

`duckdb.runtime.*` mirrors what the two services are deployed with.
`duckdb.expected_cli_version` (`1.5.4`) is checked by preflight against the
installed Python `duckdb`; the DuckLake catalog metadata schema is
version-dependent, so reading the catalog with a different DuckDB than the one
that wrote it can produce a confidently wrong answer.

> The host `duckdb` CLI on these machines is **1.5.2**, while the server's JDBC
> driver is **1.5.4.0**. That is why every SQL path in this project goes through
> `scripts/lib/duckdb_exec.py`, which uses the venv's pinned `duckdb==1.5.4`,
> and not through the CLI.

`sweeps.*` holds the engine-only (Track A) parameter sweeps, sized for ~5 GiB of
free disk. The source spec's 100M/500M-row datasets and 100 GB–1 TB compaction
tiers do not fit on an 8 GiB root volume and are reported `NOT TESTED`.

## `config/postgres.yaml`, `config/s3.yaml`

Read-only metric queries and preflight/cleanup policy. The parts that are
enforced rather than documented:

- `s3.cleanup.allowed_prefix` — `cleanup.sh` refuses to run if the prefix is
  empty, `/` or `.`, and requires typing the bucket name.
- `s3.cleanup.allow_bucket_delete: false` — present so the intent is explicit.
- `s3.auth.provider: instance_role` — no key-based path exists.

---

## `config/monitoring.yaml`

Scrape intervals and retention. The expensive scrape is the S3 `ListObjectsV2`
over the whole prefix — raise `s3_interval` before anything else if the exporter
starts costing measurable CPU.

## Changing something

| Change | Command |
|---|---|
| generator rate, batch, profile | edit `config/generator.yaml`, or pass `--rps` / `--duration` |
| collector flush or DuckDB settings | edit `config/collector.yaml` → `./scripts/deploy-collector.sh --no-build` |
| compaction schedule or sizes | edit `config/compactor.yaml` → `./scripts/deploy-compactor.sh --no-build` |
| rotate the JWT secret | `./scripts/gen-secret.sh --force` → `./scripts/deploy-collector.sh --no-build` |
| new code on 2 or 3 | `./scripts/deploy-{collector,compactor}.sh` (no `--no-build`) |
| dashboards | edit `monitoring/grafana/build_dashboards.py`, re-run it; Grafana reloads within 30 s |

After any change to the collector or compactor:

```bash
./scripts/health-check.sh
```

The effective config is captured into `results/<test-id>/environment.json` on
every run, password redacted, along with an `env_hash` — so a later reader can
tell whether two runs are comparable at all.
